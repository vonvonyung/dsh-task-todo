## 1. 一句话

在 **DSH 待办任务** 的任务菜单里加两行 —— **「转为 AI 任务台想法」** 和 **「转为 AI 任务台工作（开跑）」** ——
把一条待办任务一键变成 **AI 任务台** 的想法，或直接开工（建 worktree、起 AI 引擎）。

## 3. 为什么不把代码直接写进两个插件里

这是本方案的**核心决策**，请重点评审。

### 3.1 两个插件的客户端半边是**互相不可见**的

DSH 的每个 bundle 插件，客户端半边都是**独立的 `window.__ModuleLoader__.load({ factory })`**，
各自一个闭包，**没有共享模块图**，`import` 不通。

所以「待办的菜单渲染」和「任务台的调用能力」之间，**没有天然的调用路径**。

### 3.2 三种可选位置

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 写进待办** | 待办直接调任务台 | 少一个包 | 待办凭空多一个**可选**依赖；没装任务台的人会看到点不通的菜单，得写条件探测，逻辑变绕 |
| **B. 写进任务台** | 任务台去改待办的 UI | 少一个包 | 更糟：任务台要去背另一个插件的界面 |
| **C. 独立桥插件** ✅ 选定 | 接缝单独住一个包 | 两边互不依赖、各自独立发布；没装任一方时优雅降级 | 多一个包要维护 |

**选定 C**。理由：这是一条**可选的集成**，不该成为任一主项目的负担。
两个主项目继续各自演进，桥坏了也不影响它们。

### 3.3 桥怎么"够到"两边（关键机制）

桥**不 import 任何一方的包**，两条接缝都是**运行时**的：

```
                    ┌─────────────────────────┐
   待办任务 UI  ────▶│ window.__dshTodoTaskActions │  ← 待办提供的注册表（全局）
   （渲染菜单行）    └─────────────────────────┘
                              ▲ 注册两行
                              │
                     ┌────────┴────────┐
                     │  桥 (client.js) │
                     └────────┬────────┘
                              │ fetch 自己的 HTTP 路由
                     ┌────────┴────────┐
                     │  桥 (index.js)  │  宿主半边
                     └────────┬────────┘
                              │ HTTP POST /api/<action>（回环）
                     ┌────────┴────────┐
                     │  AI 任务台 L3   │  进程内，随机端口
                     └─────────────────┘
```

- **待办侧**：待办新增一个**正式的扩展点**（见 §4）。桥只往里注册数据，**不渲染任何东西**。
- **任务台侧**：桥用 HTTP 调它的 action（**与任务台自己的工具同一条路**），不持有它的 `AppApi`。

## 4. 待办插件的改动：新增"任务动作扩展点"

**改动量：`lib/client.js` +119 行、`scripts/verify-client-render.mjs` +125 行，纯增量、零删除。**

### 4.1 对外契约（这是跨插件 ABI，请重点评审）

```js
window.__dshTodoTaskActions.register(action) -> dispose

action = {
  id:      'aitm-idea',        // 稳定唯一；重复注册同 id = 替换
  label:   '转为想法',          // 字符串，或 (task) => string
  order:   200,                // 升序，默认 100（内置项在扩展项之上）
  enabled: (task) => true,     // 可选；返回 false 则该任务不显示此行
  run:     (task, api) => {}   // 可返回 Promise
}
```

### 4.2 三个设计决定（都被测试逼出来过）

1. **`api` 是刻意做窄的**，只有 `refresh` / `settings` / `mutate`，
   **不暴露内部 `call`**。理由：`call` 能打到待办全部 ~28 个宿主方法，
   放出去就等于把它们全变成事实上的公开 API，以后不敢改。
   → 有断言盯着 `api.call === undefined`。

2. **disposer 比对"记录"而不是 id**。第一版按 id 删，测试立刻抓到：
   插件热重载时**新注册先进来、旧的再 dispose**，会把新的那条删掉，菜单就空了。

3. **扩展项渲染在「移动到清单」之后、「删除任务」之前**。
   菜单刚变长，危险操作不该被挤到容易误点的位置。

### 4.3 测试

`scripts/verify-client-render.mjs` 从 **460 → 484 条断言**（新增 24 条），全绿。覆盖：

- 注册表存在、非法注册（空 id / 无 run）报错
- 排序、按任务 `enabled`、`enabled` 抛错只掉自己那行
- 按 id 替换、**陈旧 disposer 不误删**新注册
- **走真实菜单点击**：点卡片的「移动到清单」→ 点扩展行 → 校验拿到的 `task` 是活的、`api` 是窄的
- 抛错的 action 被兜住（转成 toast），界面不崩
- dispose 后菜单行消失

`node scripts/check-ready.mjs` → **READY：全部 47 项门禁通过**。

## 5. 桥插件的功能

### 5.1 两行菜单

| 菜单行 | 行为 | 副作用 |
| --- | --- | --- |
| 转为 AI 任务台想法 | `idea.create`（标题=任务标题；正文=备注+截止+标签） | 无 |
| 转为 AI 任务台工作（开跑） | 弹框确认指令 → `idea.create` → `task.start` | **有**：建 worktree、起 AI 引擎 |

「转为工作」会**先把拼好的指令弹出来让人确认或改**，取消即不执行——
因为这是全流程、有真实副作用的操作。

### 5.2 同时给 agent 两个工具

`todo_to_idea` / `todo_to_work`。**菜单和工具走同一段代码**（`convertTask`），
避免出现"菜单能做、agent 做不了"的两套行为。

### 5.3 降级行为（重要）

任务台**没在运行**时（没装 / 没启动），两行**仍然出现**，但显示为：

```
转为 AI 任务台想法（任务台未运行）
```

点它会得到一句人能看懂的话：*"AI 任务台没在运行：先在右侧栏打开一次「AI 任务台」，再回来点这里。"*

**为什么不用 `enabled: false` 把行藏掉**：藏了之后「插件没装」和「任务台没开」在界面上**完全一样**，
而这两件事的处理方式不同（一个去装插件，一个去打开任务台）。
留一行带说明的灰项，用户一眼知道该做什么。
—— 这正是本次开发中真实踩到的坑（见 §7），值得单独作为一个设计原则记录。

### 5.4 怎么找到任务台

任务台的端口**每次启动都是随机的**（进程内 L3，`port: 0`）。
实测：昨天 62231、今天 49182。所以**不能写死、也不能缓存到磁盘**。

桥在 `127.0.0.1` 的 **20000–65000** 扫端口，按 `256` 个一批并发，认它的 `GET /api/health`
（要求 `ok===true` 且 `actions` 是数字，避免误认别的服务）。
**实测最坏 5.2 秒**找到（目标在最后一批时）。也可以用 `AITM_URL` 显式指定。

探到后：**退避重试**（0.5s→1.5s→3s→6s→15s→30s），探到后转 **45 秒心跳**
（任务台会被关掉或重启换端口，只探一次会让菜单一直挂着一条点不通的行）。

### 6.1 当前卡点：桥加载失败

插件注册表实证：

```
entryId:    include:todo-aitm-bridge
enabled:    true
fiberPhase: "failed"        ← 加载失败，所以菜单里没有那两行
```

**我的代码本身是好的**：用桩仿真跑通 —— 导入 OK、`apply()` OK、路由与两个工具都注册成功：

```

[bridge] 桥已就绪：todo_to_idea / todo_to_work
apply OK; registrations = route:/todo-aitm-bridge, tool:todo_to_idea, tool:todo_to_work
```

所以问题在**模块解析**，不在逻辑。

### 6.2 已查明的事实，以及**尚未完全确认**的部分

**已确信的：**

- 桥的 `index.js` 第一行 `import { defineTool } from '@deepseek-ai/dsh-tools'`。
- 桥通过 `link:` 安装 → 在 profile 里是 **junction**，真实路径在 `D:\Code\Arena_progres\...`。
- 从 `D:\...` 往上走**没有任何 `node_modules`**，Node 解析不到 `dsh-tools`。
- `profiles\node_modules\@deepseek-ai\dsh-tools` 这个 junction **是断的** ——
  指向 `...\Programs\DSH Desktop\resources\app\node_modules\...`，而真实 App 目录叫
  **`DeepSeek Harness`**。于是普通 Node 解析（`createRequire` 实测）**FAIL: MODULE_NOT_FOUND**。
- **`dsh-plugin-aitm` 同样 import `dsh-tools`、同样没有 `node_modules`，却加载成功**（`active`）。
  它是 `github:` 装的**真实目录**，在 profile 里面。

**尚待实证的（诚实标注）：**

- 「junction 的真实路径逃出 profile 的解析范围，而真实目录不会」这个**假设还没有被实验确证**。
  我原本打算的验证（在 profile 里放一份真实目录副本再重启）**因为要重启 DSH、影响你正在用的环境，没有擅自做**。
- 另外，**待办插件现在能加载（`active`）很可能是个巧合**：它的仓库里有我之前为跑门禁
  照 CI 口径 `npm install` 出来的 `node_modules`（460MB、200+ 个 `@deepseek-ai/*`）。
  **如果没跑过那次安装，待办今天大概率也会是 `failed`。**
  也就是说"靠自带的 `node_modules` 存活"这条路，本身就是脆的。

### 6.3 拟定的修法（方案 2，已同意）

**让插件不再依赖解析宿主包。** 但这里有个**必须向评审说明的技术发现**：

> `defineTool` **不是**空包装。读它的实现（`dsh-tools/lib/index.js:838`）：它会把
> `parameters` / `output.schema` 这套**规格编译成 JSON Schema**（`parameterSchemaSpecToJsonSchema`
> / `valueSchemaSpecToJsonSchema`），并挂上校验函数。**直接去掉它，工具注册会坏。**

而 `ctx.get('tools')` 提供的是 `register / get / schemas / execute / guard / restrict / presentAs`
—— **没有 `defineTool`**。

所以"方案 2"的真实含义需要收敛为二选一，**请评审给意见**：

| 子方案 | 做法 | 代价 |
| --- | --- | --- |
| **2a. 干脆不注册工具** | 桥只保留**菜单**功能（这才是用户要的）；agent 工具放弃 | 最简、零依赖、零解析问题；失去 agent 侧入口 |
| **2b. 自带一份最小 schema 编译** | 桥自己把 parameters 写成 **JSON Schema 字面量**，不经过 `defineTool` | 无需宿主包；但要自己保证 schema 正确（约 20 行，可写单测） |

我倾向 **2a + 2b 组合**：**先把菜单跑通**（本次目标），agent 工具按 2b 补。
理由是菜单才是你要的东西，不该被工具那条支线拖住。

**另一个更省事的候选**（供评审参考）：
既然 `dsh-plugin-aitm` 用 `github:` 装能正常加载，那**待办和桥也用 `github:` 装**（而非 `link:`）
可能就绕开了 junction 问题 —— 但这会**牺牲本地开发的便利**（改完要 push 才能生效）。
若评审确认 junction 是根因，可以考虑：**开发用 `link:`，但给桥的仓库也留一份 `node_modules`**（代价 460MB）。

## 7. 过程中踩到的坑（建议沉淀为规范）

1. **"看不到"是最贵的一类问题。**
   本次两次卡在"菜单没有那两行"，而**原因完全不同**：
   第一次是**扩展点还没有消费者**（正常，我解释过）；
   第二次是**插件 fiber 失败**（异常）。
   两者在界面上长得一模一样。→ 所以 §5.3 才坚持"任务台没开"要**显示成一行灰项**而不是藏掉。

2. **`verify-client-render` 在并行门禁下偶发失败。**
   单跑 3 次都 484/484 全绿；`check-ready.mjs` 并行跑时**偶尔挂**。
   它是全量门禁里最慢的一项（**31–40 秒**，其余都在 300ms 内），像是超时/时序敏感。
   **既存问题，非本次引入。** 建议单独修。

3. **`docs/desktop-install.md` 已过期。**
   文档称 `dsh plugin --profile desktop add` 会被无条件拒绝（`rejectElectronProfile`），
   但**实测成功**并正确改写了 profile。建议更新文档。

4. **`profiles\node_modules` 大批 junction 断链**（指向旧 App 目录名）。
   与本次无关，但可能影响其他插件，建议排查。

5. **上游打包缺陷**：npm 上 `@deepseek-ai/dsh-tools@0.2.0-rc.2` 的 `package.json`
   **没有声明** `@deepseek-ai/dsh-sandbox`，但 `lib/index.js:7` 确实 import 它；
   而 npm 上 `dsh-sandbox` 只发布到 `0.0.1-rc.1`。→ 4 个门禁直接 `ERR_MODULE_NOT_FOUND`。
   而已用脚本绕过（见 `dsh-task-todo/.tmp-setup-gates.ps1`：从桌面版自带包 junction 一份同代 `0.1.7-rc.2`）。

## 10. 评审意见（2026-10-13）

### 10.1 总体结论

**方向可行，但目前更像已验证部分机制的 PoC 方案；建议先收敛跨插件契约和失败/权限语义，再做端到端发布。**

- **同意 §3.2 选独立桥插件 C**：这是可选集成，桥单独发布能隔离两边的依赖和故障。待办侧仍需提供一个正式、可版本化的菜单扩展点；桥侧则应只调用 AI 任务台明确支持的集成接口。
- **建议分阶段**：先让菜单可稳定地“在任务台创建想法”；然后处理“创建并启动工作”的确认、幂等和失败恢复；最后再增加 agent 工具。这样不会让工具依赖或有副作用的启动流程阻塞最基本的想法创建。
- **主要阻塞项仍是服务发现与安全边界**：随机端口全范围扫描适合验证概念，不建议未经更多验证就作为正式发现协议。同事已补充 AI 任务台源码可修改，并建议增加最小发现/身份接口；因此原稿“AI 任务台不动”的约束可以放宽，但仍需证明新接口能被独立桥跨插件调用，并覆盖版本、认证和幂等需求。
- 本评审针对方案文本，不代表桥插件或真实 DSH 环境已经通过端到端验证。设计稿所列的扩展点代码和测试明确标为“未提交、未推送”；我从远端分支 `e393ca5` 读取的代码中也尚未看到该扩展点，因此目前不能独立复核其 484 条断言或 ABI 实现。

### 10.2 对 §8 五项问题的逐项答复

1. **§3.2 选 C：基本认同。** 前提是先确认 DSH 没有可复用的宿主级插件通信/服务发现接口。若没有，独立桥是清楚的边界；但不能仅凭“客户端模块图互相不可见”就推出宿主半边也没有更稳的服务接缝。
2. **§4.1 扩展点：窄 `api` 是正确方向，但契约还不够完整。** 建议增加明确的 `apiVersion`，说明注册/替换/dispose、热重载和任务对象生命周期；逐项定义 `settings`、`mutate` 的可见范围与副作用，避免它们成为未文档化的宽权限 API。另有一个直接冲突：§5.3 要保留灰色不可用菜单项，但当前契约规定 `enabled:false` 时隐藏该行。若要保留灰项，需另设 `visible` 与 `disabledReason`（或等价状态）并测试；否则调整 §5.3 的交互承诺。
3. **§6.3：首版建议选 2a，先不注册 agent 工具。** 这能把菜单主路径与 `dsh-tools` 解析问题隔离。后续确需工具时，2b（直接提供 JSON Schema 字面量）应保留为待验证候选，不应和“复制 `defineTool` 的 schema 编译器”混为一谈。`tools.register` 的 `parameters: Record<string, unknown>` 类型说明直接传 schema 在类型上可能成立，但不能证明运行时会按预期校验或调用；需先查注册实现，再用真实 DSH 工具验证注册、schema 暴露、参数校验和执行。尤其 `todo_to_work` 会启动 AI 工作，agent 工具调用没有菜单里的人工点击，不能把 `window.confirm` 当作它的授权机制；应先有宿主级确认/审批或明确限制为仅由用户主动触发。
4. **§5.3：保留可操作的状态提示是好方向，但现有判定与文案不足。** 端口探测失败只能说明“当前没探到服务”，无法区分“没安装”“未启动”“启动/重启中”或“端口变化”。建议首版用诚实的通用提示（例如“AI 任务台当前不可用，请确认已安装并启动”）；只有存在可靠的插件安装状态来源时才区分两者。若要显示灰项，应先补齐上面提到的 `visible`/`disabledReason` 契约。
5. **§6.2 的判断：有可能，但证据尚不足以认定根因。** junction 目标路径异常和 `MODULE_NOT_FOUND` 是线索；`fiberPhase: failed` 本身不能证明失败一定发生在模块解析阶段。取得完整加载错误/堆栈后，再在隔离 profile 中用相同插件版本、相同 DSH 版本，对比 `link:` 与 `github:` 安装，以及有/无可解析 `node_modules` 的结果，才能把“路径/安装方式导致”从假设变成结论。建议不要在正在使用的 profile 上做这类验证，也不要把复制数百 MB `node_modules` 当作正式修复。

### 10.3 实现前需要收敛的 P0 问题

#### A. “转为”是移动，还是创建关联副本？

当前两项行为只创建 AI 任务台对象，没有说明会更新、完成、删除或归档原待办；因此实际语义是“复制/创建”，不是“转移”。建议首版保留原待办，使用“在 AI 任务台创建想法 / 创建工作”一类文案，并在目标对象保存来源标识和回链。若确实要“转移”，需先确定原任务的后续状态、失败时如何回滚，以及两边状态是否双向同步。

#### B. 重复提交与两步启动的部分成功

`idea.create` 后再 `task.start` 不是原子事务。请求超时可能发生在服务已创建对象、但桥尚未收到响应之后；直接重试可能产生重复想法，或再次启动工作。建议定义稳定 `sourceRef`（至少含来源插件、待办实例/配置范围和 task ID）及幂等键，并由目标 API 或桥的持久映射保证重复请求返回已有结果。不要用标题去重。对“创建成功、启动失败”要明确显示部分成功，并允许只重试启动、不重复建想法。

#### C. AI 工作启动需要明确目标与人工确认边界

文档尚未说明 `task.start` 如何确定项目/仓库、worktree 位置、引擎/模型和权限范围，也未说明这些字段缺失时的默认值。工作启动确认页建议展示最终解析后的目标、指令和副作用，而不只是可编辑指令文本。菜单路径可由用户显式确认；agent 工具路径必须另有服务端审批/授权约束，不能仅靠客户端弹框。建议在这些问题解决前，先不向 agent 暴露 `todo_to_work`。

#### D. 服务发现、身份校验和调用边界

- 扫描 `20000–65000` 不能保证覆盖 OS 为随机端口分配的范围；当前目标环境为 Windows，动态端口还可能高于 `65000`。大量本机连接探测也有耗时、误识别和被安全软件拦截的风险。
- 同事补充：现有 `/api/health` 已返回 `apiRev`、`version`、`actions`。其中 `apiRev`/`version` 可用于兼容性握手；但 `actions` 数量或列表本身不一定能确认服务身份，而且健康接口只有在桥已知道 URL/端口后才能调用，不能单独解决随机端口发现。建议补明确的服务 ID、桥协议版本与能力，并处理过期记录、启动/退出和重启换端口。
- 文档应说明本地 API 的认证、CORS/CSRF 边界和允许调用的动作。桥服务端只应允许所需的 `idea.create`、`task.start`，不要把任意 `/api/<action>` 暴露成通用转发器；`AITM_URL` 也应有明确的允许地址范围。 renderer 继续只调用桥自己的 DSH 路由，连接 `127.0.0.1` 的部分留在受控的宿主侧。
- 同事已答复：允许修改 AI 任务台，并倾向增加最小集成接口。这是比端口扫描更稳妥的方向。其提到的 `src/web/l3.ts` / `L3.invoke()` 仍需确认实际运行层和可见范围：若它只是任务台自身 bundle 内的函数，独立桥不能仅凭它存在就跨插件调用。应明确它是否注册到了 DSH 宿主可访问的服务/IPC/路由；若没有，就需要新增一个公开、版本化的宿主侧接缝或稳定发现记录。

#### E. 字段映射与版本兼容

请把传给 `idea.create` / `task.start` 的请求形状写成一个小型、版本化的集成契约：标题、备注、截止日期（日期/时区语义）、标签、原待办 ID/回链，以及工作启动需要的额外字段。优先结构化传值，不要把所有字段拼成一段无法区分的指令；同时说明重复任务、子任务、清单、附件等暂不支持还是如何映射。扩展点 API、桥协议和 AI 任务台 API 也需要最低兼容版本及不兼容时的清晰降级状态。

### 10.4 建议的验证门槛

在宣布可用前，至少验证：

- 扩展点在任意插件加载顺序、重复注册、热重载和旧 disposer 场景下都能正确显示/清理；不同 API 版本有明确降级表现。
- 服务未启动、启动/重启、端口变化、错误服务占用端口、版本不兼容时，不会把请求发送给错误目标，也不会让菜单静默失效。
- 对同一待办重复点击、超时后重试、`idea.create` 成功但 `task.start` 失败，均不会重复创建或意外重复开工。
- 取消确认时无副作用；未得到人工授权的 agent 工具调用不能启动工作；成功/部分成功/失败都有可理解的结果提示。
- 在隔离、干净的 DSH profile 中按支持的安装方式验证插件加载，不依赖开发机残留的 `node_modules` 或旧宿主路径。

### 10.5 请作者/用户确认的决策

1. 首版是否按“创建关联副本、原待办保留”实现，并把菜单文案从“转为”调整为“创建到 AI 任务台”？
2. **同事答复：允许 AI 任务台做最小改动，并建议增加发现/身份接口。** 仍待确认 `L3.invoke()` 是否对独立桥跨插件可达，以及它是否同时解决随机端口的发现；若只是内部调用方法，还需确定宿主侧公开接口或稳定发现记录。
3. 首版范围是否先限定为“菜单 → 创建想法”，暂缓工作启动和 agent 工具？如不暂缓，工作目标的默认选择及人工审批方式是什么？
4. 任务台不可用时，是否接受一个不区分“未安装/未启动”的通用状态提示？若必须区分，需要由哪一侧提供可信状态？
5. 原待办与 AI 任务台对象是否需要后续状态同步？建议首版不做双向同步，只保留来源 ID 和回链，避免形成两个互相覆盖的状态源。

## 11. 对同事回复的二次核对（2026-10-13）

### 11.1 `defineTool` 与 2b

**采纳同事的澄清。** 首版选 2a；2b（由桥直接提供 JSON Schema 字面量）应保留为待验证项，不是被评审否决。评审反对的是复制 `defineTool` 的 schema 编译实现，不是提前断言标准 JSON Schema 一定不可用。`parameters: Record<string, unknown>` 只说明类型层面较宽，仍需查看 `tools.register` 的运行时实现，并以最小测试工具验证 schema 是否正确暴露、校验和执行。

### 11.2 AI 任务台允许修改与 `L3.invoke()`

**采纳“允许 AI 任务台做最小改动，并优先用正式接缝替代端口扫描”这一方向。** 但暂不把 `L3.invoke()` 直接认定为桥插件可用的跨插件 API：

- **发现、兼容性检查、调用是三个问题。** `/api/health` 中的 `apiRev`、`version`、`actions` 可帮助桥验证一个已定位服务的版本/能力，但若端口随机，仍需一个稳定 rendezvous 告诉桥去哪里连接。
- `L3.invoke()` 可能解决动作调用，但需核实它是否属于任务台自身 web bundle 的内部函数，还是已通过 DSH 宿主注册为其他插件可调用的服务。独立 bundle 之间不能因为处于同一 DSH 进程，就假定能直接 import 或访问彼此的闭包。
- 若 `L3.invoke()` 已通过宿主 IPC/服务注册跨插件暴露，可以优先复用并补齐版本、权限和幂等契约；若没有，建议 AI 任务台增加最小的、公开且版本化的宿主路由/IPC 或受保护的发现记录，再由桥调用。不要把内部实现路径本身当成稳定 ABI。

本次复核依据同事提供的接口描述；AI 任务台源码不在当前工作区，我无法独立检查 `src/web/l3.ts` 的实现和注册位置。**因此结论是：采纳“允许并优先增加最小集成接口”，有条件采纳“`L3.invoke()` 可作为具体接缝”；后者需源码检查和独立桥调用测试后才能确认。**
