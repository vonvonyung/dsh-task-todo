# 待办任务 → AI 任务台桥接：设计与实施记录

> 状态（2026-10-13）：**待办侧 v1 任务菜单扩展 ABI 已在当前 checkout 实现；桥消费者尚未实现。** 已接受的默认方向是保留原待办、在 AI 任务台创建关联对象；先打通菜单创建想法，再处理需明确确认的工作启动，最后才考虑有审批保护的 agent 工具。AI 任务台侧优先使用受限、版本化的现有实例接口，不导出或复制 `L3` 句柄。

## 1. 一句话

在 **DSH 待办任务** 的任务菜单中提供扩展动作：第一阶段把待办**保留原样**并在 **AI 任务台** 创建关联想法；后续再通过明确确认启动工作（沿用任务台现有项目/引擎配置），最后才考虑由审批保护的 agent 工具触发工作。

## 3. 为什么不把代码直接写进两个插件里

这是本方案的**核心决策**，请重点评审。

### 3.1 两个插件的客户端半边是**互相不可见**的

DSH 的每个 bundle 插件，客户端半边都是**独立的 `window.__ModuleLoader__.load({ factory })`**，
各自一个闭包，**没有共享模块图**，`import` 不通。

所以「待办的菜单渲染」和「任务台的调用能力」之间，**没有天然的调用路径**。

### 3.2 三种可选位置

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 写进待办** | 待办直接调任务台 | 少一个包 | 待办凭空多一个**可选**依赖；没装任务台的人会看到点不通的菜单，得写条件探测，逻辑变绕 |
| **B. 写进任务台** | 任务台去改待办的 UI | 少一个包 | 更糟：任务台要去背另一个插件的界面 |
| **C. 独立桥插件** ✅ 选定 | 接缝单独住一个包 | 两边互不依赖、各自独立发布；没装任一方时优雅降级 | 多一个包要维护 |

**选定 C**。理由：这是一条**可选的集成**，不该成为任一主项目的负担。
两个主项目继续各自演进，桥坏了也不影响它们。

### 3.3 桥怎么"够到"两边（关键机制）

桥**不 import 任何一方的包**，两条接缝都是**运行时**的：

```
                    ┌─────────────────────────┐
   待办任务 UI  ────▶│ window.__dshTodoTaskActions │  ← 待办提供的注册表（全局）
   （渲染菜单行）    └─────────────────────────┘
                              ▲ 注册两行
                              │
                     ┌────────┴────────┐
                     │  桥 (client.js) │
                     └────────┬────────┘
                              │ fetch 自己的同源 HTTP 路由
                     ┌────────┴────────┐
                     │  桥 (index.js)  │  宿主半边
                     └────────┬────────┘
                              │ 受限、版本化的现有实例接口
                     ┌────────┴────────┐
                     │ AI 任务台已有实例│  不导出/复制 L3 句柄
                     └─────────────────┘
```

- **待办侧**：待办提供正式、版本化的任务菜单扩展点（见 §4）。桥只注册动作，不负责渲染待办菜单。
- **任务台侧**：桥优先经受限接口调用其已运行的实例；不能把 `/api/<任意 action>` 做成通用转发器，也不应通过 `createL3()` 建第二个实例来假装复用。

## 4. 待办插件的改动：v1 任务菜单扩展点

扩展点已在当前 `dsh-task-todo` checkout 实现，菜单集成位于 `lib/client.js`；测试扩展位于 `scripts/verify-client-render.mjs`。

### 4.1 对外契约

```js
window.__dshTodoTaskActions = {
  apiVersion: 1,
  register(action) -> dispose,
  subscribe(listener) -> unsubscribe,
  forTask(task) -> visible menu rows,
}

window event: 'dsh-todo-task-actions-ready'

action = {
  id: 'aitm-idea',                         // 非空稳定 ID；同 ID 注册会替换
  label: '在 AI 任务台创建想法',             // 字符串，或 (task) => string
  order: 200,                               // 升序；默认 100，ID 用作同序 tie-break
  visible: (task) => true,                 // 可选；false 时隐藏该行
  enabled: (task) => true,                 // 可选；false 时显示灰色禁用行
  disabledReason: 'AI 任务台当前不可用',    // 可选字符串或 (task) => string
  run: async (task, api) => '已创建想法',    // 可返回 Promise；非空字符串显示为 toast（最多 180 字符）
}
```

API 发布后派发 ready 事件，方便先加载的扩展等待；后加载的扩展直接读取全局对象。若全局上已有不同版本或不完整的 API，v1 会 fail closed 并保留现有对象，不会降级覆盖它。`task` 是深拷贝并冻结的快照，不是内部 store 句柄。菜单在“移动到其他清单”之后、“删除任务”之前渲染扩展项。`visible`/`enabled`/`label`/`disabledReason` 的异常或异步返回不会击穿待办 UI：异常动作会被跳过并记录诊断；`enabled:false` 保留为可解释的灰项。

### 4.2 回调权限与生命周期

`run(task, api)` 的 `api` 仅包含：

- `refresh()`：刷新当前待办视图。
- `settings`：冻结的偏好子集，仅 `appearance`、`weekStart`、`defaultList`、`badgeCount`。
- `mutate(method, args)`：限制到菜单所选的当前任务；只允许 `toggle`、`move`、`update`、`addSubtask`。`update` 字段限于 `title`、`note`、`due`、`start`、`priority`、`tags`。成功时只返回变更任务/子任务的冻结快照，失败返回 `null`；不泄露 host mutation 回包中的完整 view state、其他任务或文件路径，也不提供删除、任意 host 方法、`call` 或工具执行入口。

注册表替换会通知订阅者，菜单可在打开状态下更新。`dispose()` 只在原记录仍是当前记录时才移除它，因此热重载后的旧 disposer 不会误删新版本。动作执行的同步/异步异常由待办捕获并显示 toast；非空字符串返回值也可用作成功状态提示。

### 4.3 实现与测试决定

1. **窄 API**：不暴露内部 `call`，避免将待办全部 host 方法意外固化成跨插件 ABI。
2. **可解释的不可用状态**：`visible` 和 `enabled` 分开；不可用服务可显示灰色行及原因，而不是被静默隐藏。
3. **安全的替换/注销**：disposer 比对记录身份，不只比较 ID。
4. **加载顺序与动态更新**：ready 事件、`subscribe` 和 `forTask` 覆盖先加载、后加载以及菜单打开期间注册/注销。
5. **危险操作位置**：扩展项位于清单移动选项之后、删除任务之前。

`scripts/verify-client-render.mjs` 从基线的 **460** 增至 **489** 项（新增 29 项）。新增覆盖包括事件加载顺序、排序、显隐/禁用、非法注册、替换与 stale disposer、菜单即时更新、扩展项相对删除操作的位置、冻结快照、回调 API 边界、任务 ID 作用域、mutate 回包隔离、状态 toast、错误隔离及不覆盖不兼容 API 版本。当前使用 React 19.3.0 时为 **489/489 全通过**；全量 gate 结果见 §6。

## 5. 桥插件的分阶段行为

### 5.1 阶段一：从待办菜单创建关联想法

首个可交付行为是**在 AI 任务台创建想法**，不是“转移”待办：原任务保留、状态不变。目标对象应保存稳定的来源标识和回链，避免重复点击生成重复对象；标题、备注、截止日期和标签的映射需由桥 API 契约明确。

当前只完成待办端扩展 ABI；桥仓库公开但为空，尚无菜单消费者或端到端创建实现。

### 5.2 阶段二：明确确认后创建并启动工作

启动工作有真实副作用（例如创建 worktree、启动引擎），必须先展示并要求用户明确确认，取消时不得创建或启动任何内容。目标项目、引擎/模型和其他工作配置应沿用 AI 任务台**现有项目与引擎配置**，不得由待办桥硬编码或静默猜测。确认界面要展示最终解析出的目标配置与指令。

`idea.create` 与 `task.start` 不是原子操作：实现时还要处理幂等、超时重试，以及“想法已创建但启动失败”的部分成功状态。具体调用流程待受限 AI 任务台接口确定，当前尚未实现或实测。

### 5.3 阶段三：审批保护的 agent 工具

先不注册 `todo_to_work` 等 agent 工具。后续若增加工具，必须复用明确的映射/幂等逻辑，并由宿主侧审批/授权保护有副作用的工作启动；菜单里的浏览器确认框不能充当 agent 调用的授权边界。工具 JSON Schema 与运行时校验也须单独验证。

### 5.4 任务台发现与调用边界

优先为 AI 任务台现有实例提供**受限、版本化**的发现与调用接口。现有 `/aitm-plugin/config` 可作为同源发现的调查起点，但响应含诊断信息，不能未经收敛就当作跨插件 ABI；调用也应限制在所需能力，不暴露任意 action 转发。不能从桥直接 import `createL3()` 来替代现有实例，也不能导出/复制私有 `L3` 句柄。

桥的浏览器代码只访问同源相对路由；连接 AI 任务台的本机/服务端调用应留在受控的宿主侧，不能让用户浏览器去请求 `localhost`。随机端口扫描不是默认发现方案；只有经安全与可移植性评估后，才考虑作为诊断/回退机制。

### 5.5 不可用状态

若 AI 任务台接口当前不可用，扩展项应保留为灰色禁用行并给出诚实、通用的恢复提示（`enabled:false` + `disabledReason`），不要把“未安装”“未启动”“重启换端口”误判为可区分的状态。菜单文案使用“创建”而不是“转为”，避免暗示原待办会被移动或删除。

## 7. 过程中踩到的坑与环境备注

1. **“没有菜单行”不等于同一种故障。** 没有消费者注册时是正常的空菜单；消费者注册了但服务不可用时，应保留灰色禁用项和恢复原因；插件自身加载失败则应由宿主日志诊断。UI 不能把这些状态混为一谈。

2. **客户端 gate 对 React 版本有要求。** 测试 harness 将 React element 的 `ref` 从 props 绑定到模拟 DOM，依赖 React 19 的 ref-in-props 形状。React 18.3.1 会让 refs 为空并造成 9 项 sidebar/keyboard 假失败；React 19.3.0 下客户端 489/489、全量 gate 10/10 均通过。

3. **旧 DSH Desktop 安装记录仅作历史上下文。** 其中关于 `docs/desktop-install.md` 的 `rejectElectronProfile`、实际安装方式等来自另一台机器/会话；本 sandbox 未复现，不能当作当前桥仓库状态或根因结论。

4. 旧稿中关于 profile junction 断链的记录没有在当前 sandbox 复核；本次实现不依赖那些桌面机路径。

5. **上游 peer 包依赖需按当前 registry 核实。** 2026-10-13 查询 `@deepseek-ai/dsh-tools@0.2.0-rc.2` 时，其 `dependencies` 未列出 `@deepseek-ai/dsh-sandbox`；但 npm 已列出 `dsh-sandbox@0.2.0-rc.2`（旧稿称“只发布到 `0.0.1-rc.1`”已过时）。本次仅为运行本地验证，以 `--no-save --package-lock=false` 安装工具、sandbox、React 与 `fflate`；这些依赖不属于本次源码改动。

## 8. 已收敛的设计决策

1. **采用独立桥插件**；待办只提供窄任务菜单 ABI，不直接依赖 AI 任务台。
2. **先实现菜单创建想法**，保留原待办并保存关联来源；不把“创建”称为“转移”。
3. **工作启动必须明确确认**，确认前展示实际项目/引擎配置；使用 AI 任务台现有配置，不硬编码。
4. **agent 工具后置**，且需要宿主侧审批/授权；浏览器确认不构成 agent 的安全边界。
5. **优先调用受限、版本化的 AI 任务台现有实例接口**；不暴露或复制私有 `L3` 句柄，也不开放任意 action 转发。
6. 服务暂不可用时显示灰色禁用行和通用提示；没有可信来源时不区分“未安装”和“未启动”。

## 10. 评审意见（2026-10-13）

### 10.1 总体结论

**方向可行，但目前更像已验证部分机制的 PoC 方案；建议先收敛跨插件契约和失败/权限语义，再做端到端发布。**

- **同意 §3.2 选独立桥插件 C**：这是可选集成，桥单独发布能隔离两边的依赖和故障。待办侧现已实现正式、版本化的 v1 菜单扩展点；桥侧应只调用 AI 任务台明确支持的集成接口。
- **建议分阶段**：先让菜单可稳定地“在任务台创建想法”；然后处理“创建并启动工作”的确认、幂等和失败恢复；最后再增加 agent 工具。这样不会让工具依赖或有副作用的启动流程阻塞最基本的想法创建。
- **待实现项是受限的服务发现与调用接口**：源码核验发现，AI 任务台已有同源 `GET /aitm-plugin/config` 路由为自己的面板提供随机 L3 URL；它可用于调研，但响应含诊断信息，尚非承诺的跨插件 API。已接受的方向是收敛成窄、版本化接口；直接 `L3.invoke()` 只对持有实例的 AI 任务台插件代码可用，并未暴露给桥。
- 本评审针对方案和源码边界，不代表桥插件或真实 DSH 环境已经通过端到端验证。当前 checkout 已实现并可复核待办侧 ABI；`verify-client-render.mjs` 在 React 19.3.0 下 489/489 通过，`npm test` 的 10 个 gate 全部通过。桥仓库当前公开但为空，尚无消费者代码可独立审查。

### 10.2 对评审意见与实现边界的逐项答复

### 10.3 P0 设计约束与仍待实现的项目

#### A. 保留原任务并建立来源关联（已采纳，待桥实现）

首版在 AI 任务台创建关联对象，原待办保留且状态不变；菜单文案使用“创建”，不暗示“转移”。桥实现仍需定义稳定 `sourceRef`、来源回链及重复提交行为。若未来要做双向状态同步或真正转移，需另行约定失败回滚与状态所有权。

#### B. 重复提交与两步启动的部分成功

`idea.create` 后再 `task.start` 不是原子事务。请求超时可能发生在服务已创建对象、但桥尚未收到响应之后；直接重试可能产生重复想法，或再次启动工作。建议定义稳定 `sourceRef`（至少含来源插件、待办实例/配置范围和 task ID）及幂等键，并由目标 API 或桥的持久映射保证重复请求返回已有结果。不要用标题去重。对“创建成功、启动失败”要明确显示部分成功，并允许只重试启动、不重复建想法。

#### C. 工作启动配置与人工确认（用户已确认，接口待实现）

启动工作时沿用 AI 任务台已有项目/引擎配置，不由桥静默选择或硬编码。确认界面应展示最终解析的目标、引擎/模型、指令和副作用；用户明确确认前不得创建/启动，取消无副作用。agent 工具路径另需服务端审批/授权；菜单弹框不能充当 agent 的授权边界，因此 `todo_to_work` 暂缓。

#### D. 服务发现、身份校验和调用边界

- 扫描 `20000–65000` 不能保证覆盖 OS 为随机端口分配的范围；旧 Windows 环境记录中动态端口也可能高于 `65000`。大量本机连接探测还有耗时、误识别和被安全软件拦截的风险，因此不作为默认发现方案。
- 同事补充：现有 `/api/health` 已返回 `apiRev`、`version`、`actions`。其中 `apiRev`/`version` 可用于兼容性握手；但 `actions` 数量或列表本身不一定能确认服务身份，而且健康接口只有在桥已知道 URL/端口后才能调用，不能单独解决随机端口发现。建议补明确的服务 ID、桥协议版本与能力，并处理过期记录、启动/退出和重启换端口。
- 文档应说明本地 API 的认证、CORS/CSRF 边界和允许调用的动作。桥服务端只应允许所需的 `idea.create`、`task.start`，不要把任意 `/api/<action>` 暴露成通用转发器；`AITM_URL` 也应有明确的允许地址范围。 renderer 继续只调用桥自己的 DSH 路由，连接 `127.0.0.1` 的部分留在受控的宿主侧。
- **源码核验结果（AI 任务台分支 `arena/01a0fd0e-ai-tasks-mgr`，commit `89c7d18`）：** `src/web/l3.ts` 的 `createL3()` 在调用者的 DSH 宿主进程内创建 `AppApi`，返回的 `l3.invoke()` 直接调用 `app.invoke()`，不经过 HTTP。现有 `dsh-plugin/index.js` 把这个对象保存在模块私有的 `state.l3`，其内部 `call()` 才调用 `state.l3.invoke()`；没有把该句柄注册到 DSH `ctx`、全局对象或其他插件可见的服务。因此 `L3.invoke()` 是“AI 任务台插件内部的进程内调用”，**不是现成的跨插件 API**。同文件导出的 `ensureBase()` 只返回 URL，不暴露 `L3` 句柄。
- 同时发现现有宿主路由 `GET /aitm-plugin/config` 会调用 `ensureBase()` 并返回随机 `base` 和 `identity`，AI 任务台自己的客户端已用它发现后端地址，再请求 `/api/health`。这为同一 DSH web origin 下的桥客户端提供了可复用的 rendezvous 候选，但当前响应还包含仓库路径、日志等诊断信息，不宜不加收敛就当成跨插件公共 ABI。建议增加窄化、版本化的发现响应；若桥需要真正进程内直调，则要由任务台通过 DSH 宿主服务/IPC 显式注册一个受限的 API。

#### E. 字段映射与版本兼容

请把传给 `idea.create` / `task.start` 的请求形状写成一个小型、版本化的集成契约：标题、备注、截止日期（日期/时区语义）、标签、原待办 ID/回链，以及工作启动需要的额外字段。优先结构化传值，不要把所有字段拼成一段无法区分的指令；同时说明重复任务、子任务、清单、附件等暂不支持还是如何映射。扩展点 API、桥协议和 AI 任务台 API 也需要最低兼容版本及不兼容时的清晰降级状态。

### 11.2 AI 任务台允许修改与 `L3.invoke()`：源码核验

**已检查 AI 任务台分支 `arena/01a0fd0e-ai-tasks-mgr`，commit `89c7d18`。结论：`L3.invoke()` 是进程内直连，但只在持有该 L3 实例的 AI 任务台插件代码中可用；不是已注册给其他插件的跨插件 API。**

- `src/web/l3.ts:8–20, 72–88, 136–140`：`createL3()` 在调用者所在的 DSH 宿主进程中创建 `AppApi`，并返回 `L3` 对象。`invoke(action, payload)` 直接调用闭包里的 `app.invoke(...)`，不经过 HTTP；`base`/`port` 则对应另开的回环 HTTP 服务。
- `dsh-plugin/index.js:190–203, 1387–1394, 1464–1497`：AI 任务台的 DSH 插件把该实例保存在模块私有的 `state.l3`，其私有 `call()` 在进程内模式下调用 `state.l3.invoke()`。没有将实例挂到 `ctx`、全局对象或 DSH 可发现的服务注册表。`ensureBase()` 虽是模块导出，但只返回 URL，不返回 L3 实例；`package.json` 也没有导出 L3 子路径。其他插件不能仅凭同在一个 Node 进程，就取得这份闭包中的对象。
- 因此，桥若直接 import `createL3()`，得到的是**新建的第二个 AppApi/L3 实例**，不是取得正在运行的实例；不应这样做来共享任务台状态。若需要真正的进程内直调，AI 任务台必须显式向 DSH 宿主注册一个受限、版本化的服务，并让桥通过宿主提供的接口获取它。
- **发现方面有一个现成候选。** `dsh-plugin/index.js:1802–1848` 在宿主 `webServer` 注册稳定路径 `/aitm-plugin/config`；它会调用 `ensureBase()`，返回随机 `base`、`identity` 及若干诊断信息。`dsh-plugin/client.js:136, 2230–2247` 的面板正是先相对请求该路径，再向 `${base}/api/health` 查询身份。因此，同一 DSH web origin 下的桥客户端可能复用这条 rendezvous，避免端口扫描；但需在桥的真实运行环境验证可达性。现有响应还含仓库路径、日志等信息，不适合未经收敛就当作跨插件公共 ABI。建议另提供窄化的、版本化的发现响应。
- 如果桥走 HTTP，`src/core/server/http.ts:42–52` 当前对本机 API 设置 `Access-Control-Allow-Origin: *`，且 `/api/<action>` 可调用全体 `ACTIONS`。这不是桥的授权边界：不要暴露任意 action 转发；至少限于明确白名单，并为启动工作等写操作落实人工审批/权限策略。直接暴露 `L3.invoke()` 同样是宽权限，因为其参数是任意 action 字符串。

**最终判断：采纳“允许并优先增加最小集成接口”；不采纳“现有 `L3.invoke()` 已能被桥直接调用”。** 首选先验证并正式化同源发现路由，再让桥走受限 HTTP 接口；只有确实需要进程内直调时，才新增 DSH 宿主侧服务注册。以上是对 commit `89c7d18` 的静态源码核验，尚未在 DSH 中实测另一个插件能否访问 `/aitm-plugin/config`。
